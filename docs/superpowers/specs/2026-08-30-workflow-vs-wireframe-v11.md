there is a good reason the design interface should be similar."*

Source of truth: `Wireframe/admin-portal-nar1/wireframe_v11.html`, screens

---

## Summary

Twenty-two differences. **Three are deliberate and stay** (with the reason
recorded). Nineteen are drift.

The single largest gap is not styling: the Submission stage has **no Download
NAR1 button at all**, which Levi asked for by name on 2026-08-30 ("the download
nar1 button on the submission page should download the NAR1 pdf file filled by
you"). The backend endpoint exists and serves the facsimile; nothing calls it
from that screen.

## Kept, with reasons

| v11 has | Build does | Why the build is right |
|---|---|---|
| "Case activity — audit trail" timeline on Confirmation | nothing | Levi 2026-08-26: the trail is complete in the Audit Log module, and two places to check what happened is worse than one. Already recorded in `CaseWorkflowPage.jsx`. |
| One "Send verification email to" text input | `RecipientPicker` — every director, as removable chips | Supersedes v11. One email goes to **every** current director (`nar1_cases.default_recipients`); a single-address field cannot express a three-director board. |
| "Choose the signatory" radio list of eligible people | one fixed row naming the logged-in user | **Q1, shipped today.** A NAR1 is signed with the session's own e-Service credential and no other, so there is nothing to choose. v11's `pick-sig` (its *signed* state) is the shape that survives. |

## Proposed order

Four blocks, each shippable and testable on its own.

1. **Block A — Signing** (3.1–3.5). The screen Levi called out, and the one Q1
   just changed. Do it while that is fresh.
2. **Block B — Submission** (4.1–4.4). Contains the Download NAR1 button, which
   is an outstanding explicit request rather than drift.
3. **Block C — Data Verification + Client Verification** (1.1–1.6, 2.1–2.4).
4. **Block D — Header + Confirmation** (H1–H2, 5.1–5.2).

Every block ships with Vitest coverage, per the repo's cross-cutting rule.

## Open question

**H2 — what does the header's Save button save?** v11 puts `Save` beside
`Restart verification`, but the built workflow has no pending edits at the page
level: each stage writes immediately (`PATCH /cases/{id}` on toggle, on capacity
choice, on method change). A Save that saves nothing is worse than no Save.
Either it goes, or the stages become dirty-tracked forms. **Needs Levi's call
before Block D.**
