# Email, the recipient lock and the client-verification flow

_Moved out of `CLAUDE.md` verbatim (nothing edited) so it is not loaded into every agent turn. Read it before changing: email sending, the test-environment recipient lock, DNS probe, delivery polling, the verification letter, revisions, password reset, middleware order._

> **`APP_ENV` is the single switch, and it is invisible from outside Railway.** Set it to exactly `prod` only on the PROD services. Anything else — including unset — is non-production, which is the safe direction. **`GET /health` reports the derived answer** (`"environment": "production" | "non-production"`), unauthenticated, so this is checkable in one request without a token or Railway access. Check it after every deploy: on 2026-08-30 the **DEV** service was running `APP_ENV=prod`, which disarmed the recipient lock below while sitting on 4,398 real director addresses, and the only visible symptom was a TEST badge that never appeared in the header.

> **MIDDLEWARE ORDER IN `main.py` IS LOAD-BEARING, and it reads backwards.** `add_middleware` inserts at the FRONT of the stack, so the middleware added **last** ends up **outermost**. `api_errors.install(app)` must therefore be called **before** `app.add_middleware(CORSMiddleware, …)`, or the whole thing is decoration.
>
> Why it matters: an unhandled exception in a FastAPI app is answered by Starlette's `ServerErrorMiddleware`, which sits **above** the user middleware. That reply carries no `Access-Control-Allow-Origin`, so the browser refuses to hand it to the page at all — `fetch` **rejects** rather than resolving, and `lib/api.js` prints *"Could not reach the server … the API may be down or still starting up"* for a server that answered in 40ms. **Registering an `Exception` handler does not fix this**: Starlette hands that handler to `ServerErrorMiddleware` itself, so the nicer reply is produced in exactly the same place. Only a middleware **inside** CORS works, which is what `ErrorEnvelopeMiddleware` is.
>
> A Postgres constraint violation (`22P02`, `23503`, `22001`, …) is a fact about the **submitted data**, so it comes back as a **422 quoting the constraint** — re-sending the identical request cannot succeed, and the operator has to be told which value. Everything else is a bug: one fixed sentence to the caller, the traceback to stderr where Railway keeps it. This is how "Could not reach the server" was diagnosed on 2026-09-04: a free-text Share Class box sent `"1"` at a `uuid` column, and the message named the one thing that was not wrong.

> **The test-environment recipient lock (Levi 2026-08-30).** Whenever `APP_ENV` is not exactly `prod`, every message is delivered to a **hardcoded list** — `levi@zenexflow.com`, `roy@zenexflow.com`, `brian@getstarted.hk`, `vanis@getstarted.hk`, `jacqueline@getstarted.hk` (added 2026-10-03, test/DEV only like the rest) (`services/email_service.py`, `TEST_RECIPIENTS`) — and to nobody else. It is a module constant, not configuration: the requirement was that it be *impossible*, not merely configured, for a client to be mailed from a test deployment, and DEV's Supabase carries 4,398 real director addresses. **`EMAIL_REDIRECT_TO` has been removed**; setting it again does nothing. The substitution happens inside `send()`, below every caller, and a second assertion re-checks the outgoing list immediately before the HTTP call.
>
> The Client Verification screen still shows and still selects the **real** director addresses — that fan-out is the thing being tested — and carries a note saying nothing will reach the client. The audit row records `intended_to` (the directors) and `to` (the test recipients) separately, so the trail never claims a client was told.

> **`EMAIL_TRANSPORT` was REMOVED on 2026-08-30.** Its only value, `console`, stubbed mail out — stderr, nothing delivered, success reported — and existed solely because `RESEND_API_KEY` was a placeholder. With a real key in place that reason is spent, and protecting clients was never its job (the recipient lock above does that unconditionally). **`resend` is now the only transport, and setting `EMAIL_TRANSPORT` to anything raises at config time** rather than silently sending; the refusal names the removal so nobody hunts for a typo in a value that was correct last week. Audit rows written while it existed still read `transport: "console"`, meaning nothing was delivered, and the router still passes that through — do not normalise it away. **Do not reintroduce it:** if some future environment must suppress mail, suppress it somewhere that cannot report a delivery that did not happen.
>
> One verification email goes to **every current director** with an address on record (`nar1_cases.default_recipients`), not to a single contact. Directors with no address are still returned, carrying the reason, so a three-director board can never render as a two-director board.

> **THE COPY IS `renewal@getstarted.hk`, AND THE CASE WORKER IS NO LONGER CC'd** (Levi, 2026-09-08). This **reverses** *"the case worker is CC'd"* (2026-08-30), under which `POST /cases/{id}/verification/send` put `user["email"]` — whoever pressed Send — on the CC line of a letter about a client's statutory return. Two things were wrong with that: the client saw an individual staff member's personal address on a formal filing notice, and GSHK's record of what it told that client lived in one person's mailbox, leaving with them when they were on leave or off the account. The copy is now `email_service.CLIENT_CC`, a **module constant** exactly like `TEST_RECIPIENTS` and for the same reason — which address hears about a client's return is not a per-deployment setting somebody can repoint by editing a Railway variable.
>
> **It is on EVERY message, where the case worker's copy was on the first only.** That rule existed so three directors would not mean three identical mails in one inbox, but these messages are *not* identical — each carries its own approval link and greeting — and a shared mailbox holding the first of three would misrepresent a partial send as a complete one. `renewal@` is a record, so it gets the whole record.
>
> **`reply_to` is still the case worker, deliberately — but it is now the SAFETY NET, not the asked-for path.** Since 2026-09-08 the letter tells the client that replies are **not monitored** and to write to `renewal@getstarted.hk`; it is nonetheless sent from `no-reply@getstarted.hk`, and a client who replies regardless must reach a human who knows the case rather than a black hole. The copy going to the team while a stray answer goes to a person is the intended split. Read `user.get("email")`, never `user["email"]` — identities are cached for 30s and one written before the key existed must not break a send.
>
> **The screen names the address, and a test stops the two drifting.** The note on Client Verification promises `renewal@getstarted.hk` by name *before* the send exists, so it cannot read the value off a response — it repeats the constant in `StageClientVerification.jsx`. `test_client_cc_matches_the_screen` reads that JSX and fails if it ever stops matching `email_service.CLIENT_CC`.
>
> **A CC is a recipient, so the non-production lock binds it too**: `_apply_test_cc_lock` **drops** it outside prod rather than redirecting. That is now load-bearing in a way it was not before — `renewal@getstarted.hk` is a **real GSHK mailbox and deliberately NOT one of the `TEST_RECIPIENTS`**, so a test deployment must never reach it. (The old reasoning, "the four are already on `to` and copying them again puts one mailbox on both lines", described the case worker and no longer applies.) The guard before the HTTP call checks `to` **and** `cc`. The audit row records `cc` and `intended_cc` separately, so a dropped copy is never logged as a delivered one.

> **Resend answers 200 for an address that cannot exist, so the send probes DNS first** (Levi, 2026-09-08). A verification mailed to a made-up domain reported **total success** on the Client Verification screen: the address was well-formed so the syntax gate passed it, Resend accepted it and bounced it out of band minutes later, and `EmailError` — which only fires on HTTP ≥ 400 — had nothing to catch. `email_service.undeliverable_reason()` now asks whether the domain can receive mail at all (MX, or the A/AAAA fallback RFC 5321 §5 allows) and the router drops the ones that cannot, reporting them in the **same `failed` list** as a malformed chip and a Resend rejection — the operator's question is "who did not get it", and the answer must not depend on which of three ways an address failed.
>
> **It runs after both recipient branches, on purpose.** The syntax gate only ever ran on addresses an *operator typed*, which left the commoner case unchecked: a director address out of Viewpoint on a since-lapsed domain went to Resend unexamined.
>
> **SILENCE IS PERMISSION.** A timeout, a resolver that will not answer, no network, an unexpected library error — every uncertain result lets the address through. A wrongly withheld verification stalls a statutory filing on a director who was never written to, which is far worse than a bounce. Only a definitive *"does not exist"* / *"does not accept email"* refuses, and even then the rest of the board is still mailed.
>
> **What the pre-send check cannot do** is a real domain with a dead mailbox (`nosuchuser@gmail.com`), which is indistinguishable from a live one until delivery is attempted. That is closed by the delivery check below — **not** by a bounce webhook, which was considered and rejected.

> **Delivery is POLLED, not pushed — there is no webhook, and that is deliberate** (Levi, 2026-09-08). `email_service.delivery_status()` asks `GET https://api.resend.com/emails/{id}` for the message's `last_event`. That is the same fact an `email.bounced` webhook would deliver, **asked for instead of waited for**, and it needs **no public endpoint, no signing secret, no Resend dashboard registration and no new environment variable** — it reuses the `RESEND_API_KEY` already sending the mail, so it works on DEV and PROD the moment it deploys. A webhook would have needed all four, plus a second registration because DEV and PROD share one Resend account.
>
> **The status vocabulary is Resend's `last_event`, sorted into three answers.** Arrived: `delivered`, `opened`, `clicked`, and `complained` (it reached the mailbox and the reader pressed spam — worth saying, **not** a delivery failure). Failed: `bounced`, `failed`, `canceled`, and **`suppressed`** — the quiet one this check earns its place on, because an address that hard-bounced for anyone on the account is suppressed, and a later send to it returns 200 with an id and is never attempted. Pending: `sent`, `queued`, `scheduled`, `delivery_delayed`.
>
> **UNCERTAINTY IS ALWAYS "PENDING", NEVER "FAILED"** — a timeout, a 5xx, an unreadable body, an event name Resend adds later. Telling an operator a return bounced when it did not would have them re-send a statutory notice to a client who already has it, **and every re-send reissues the whole case's approval links**, so the rest of the board gets asked again.
>
> **`GET /cases/{id}/verification/delivery`** (`nar1:read` — it changes nothing, and someone who may read a case may see whether its letters arrived) reports one row per director. It reads the newest `EMAIL_SENT` audit row for the case and asks Resend about each message. Note the id space: a NAR1 audit row carries the **case** in `entity_id` and the **company** in `case_id`, so filtering on `case_id` would return the whole company's trail and could report on a different year's return.
>
> **The per-recipient map lives in `metadata.deliveries`** (`[{email, name, message_id}]`), written by the send. `message_ids` alone cannot serve: it drops falsy ids, so its positions stop matching `intended_to` the moment one send returns without one, and pairing them would attribute a bounce to the wrong director. It is JSONB, so **no migration was needed**. Sends made before 2026-09-08 have no `deliveries` and are reported `unknown` rather than guessed at.

> **The Send button opens a sending splash, and it is time-bounded on purpose** (Levi, 2026-09-08: *"we should actually wait for the resend to confirm the status of each email that is sent before allowing user to proceed"*). `VerificationDeliveryModal` polls the endpoint above every 3s, showing each director resolve `Sending… → Delivered ✓ / Not delivered ✗`, and the Done button stays disabled until Resend has reported.
>
> **It never blocks indefinitely.** Delivery confirmation has no upper bound — greylisting, queue retries, a bounce hours later — so at **60s** it stops asking, **names** the unresolved recipients and says plainly that this is *not* a failure. A hard bounce is normally known in seconds, because the receiving server rejects during the SMTP conversation, so the window catches the case it exists for. A **failed poll is not a failed delivery** and must never colour a director's row red.
>
> `onChanged()` is deferred to the splash closing, not fired on the send: refreshing the case underneath the modal would advance the stage behind it. A send whose response carries no `deliveries` skips the splash entirely and behaves as before.
>
> **A REDIRECTED SEND IS NEVER REPORTED AS DELIVERED, and this is the subtlest trap on the whole path.** Outside production the recipient lock substitutes `TEST_RECIPIENTS` *inside* `send()`, so Resend's record for that message describes the internal test mailboxes — **not** the address the operator chose. Printing Resend's `delivered` beside the intended address told Levi on 2026-09-08 that `levi214839824@zenexflow.com`, an address he knew did not exist, had been **Delivered**. Resend was not wrong; the pairing was. Verified against that exact send: both messages' `to` came back as the four test recipients.
>
> `deliveries` therefore records **`delivered_to` and `redirected`** alongside the intended address — the same reason the audit row carries both `to` and `intended_to`. A redirected entry gets status **`redirected`**, reads *"Not sent (test)"*, is **not green**, and **Resend is not asked about it at all**, because its answer could only describe somebody else's mailbox.
>
> **So bounce detection cannot be exercised on DEV**, and the screen now says so rather than implying a pass. The lock replaces every address with the test mailboxes, which are real and deliver; only production can confirm delivery to a client address.

> **The splash opens on the CLICK, not on the response.** The send fills a nine-page AcroForm, issues a token per director and makes one Resend call each, so there is a real multi-second gap — and until 2026-09-08 nothing appeared during it, so the button read as dead (Levi: *"there seems to be a lag between when i click on the send button and the popup appearing"*). It opens seeded from the chips, which are exactly who is about to be written to. **It does not poll until the send returns** (`phase`): there is no audit row yet, and asking early would read the PREVIOUS send on that case and report a fresh one as already settled. The 60s clock starts when polling does, not when the modal opened. A **refused** send takes the splash down, or the page banner would be drawn behind the overlay.
>
> **No unit test may resolve a real domain.** `conftest._no_dns_in_tests` stubs the probe for the whole suite. Nearly every fixture address here is at `example.com`, which is IANA-reserved with a **Null MX** and therefore genuinely undeliverable — live, the real probe would drop those recipients and fail dozens of unrelated assertions on correct code. Tests that want a specific answer re-patch the same name; the tests *of* the probe capture the real function at import time (`_probe`), since the autouse stub would otherwise make them assert on a mock.

> **The client-facing email is table-based with inline styles, on purpose** (`email_service.verification_email`). Outlook renders mail through Word: no flexbox, no grid, and no `<style>` block you can rely on. Outfit does not load in most clients, so the fallback stack *is* the typography. Tests in `test_email_service.py` assert each of these; do not "modernise" the markup.
>
> **Its wording is `docs/Auto email - NAR1 Review_v2.pdf`, verbatim** (Levi 2026-09-08). This **supersedes `docs/Confirmation NAR1 Notice.pdf`**, the hand-sent letter the message carried until then, and four of the differences are decisions rather than restyling: it opens **"Dear Client"** and not a director's name; it is signed **"Kind regards, Get Started HK Limited"** with **no case worker and no "Account Manager"** (`verification_email` therefore takes **no `recipient_name` and no `sender_name`** — they were removed, not ignored); it states that **replies are not monitored** and points changes at **`renewal@getstarted.hk`** (`email_service.RENEWAL_MAILBOX`, which `routers/public_approval.py` imports rather than re-typing); and the **HK$1,000** fee is for changes requested **after filing**, which is a later event than the "any amendments later" the old letter charged for. The page references (**Page 2** Share Capital, **Page 5** Director's Details, **Schedule 1** Shareholder's Details, **Continuation Sheet C** *if applicable*) are **hardcoded and correct**, because CR's form is static and a section keeps its page whether or not it has content. They are only true while the renderer emits all nine pages; if it ever goes back to dropping empty ones, this letter misdirects every client.
>
> **THE "NO LINK AT ALL" RULE IS REVERSED** (Levi 2026-09-01). It read: *"the client confirms by replying, and a mail about someone's company filings that contains a link is the exact shape of the phishing it would train them to trust."* The reasoning still stands; what changed is that replying by hand was the **only** way to answer, so every approval waited on a staff member reading a mailbox and a client who never replied left a case parked with nothing recorded. The message now carries a **Confirm NAR1** button (`routers/public_approval.py`). What answers the original objection, rather than going around it: the link's `GET` **mutates nothing** and says so, so the mail-security gateway that fetches every link cannot approve anything; and the page asks for **no credential, no password, no payment detail**, so there is nothing on it worth phishing for. `approval_url` is `None` when the deployment cannot build one, and the letter then asks for a **reply** instead — the only place its wording departs from the sample, because "click Confirm below" beside no button is worse than a sentence the sample does not contain, and the automated/"replies not monitored" line is **withheld** on that path for the same reason.
>
> **The reply path is no longer what the client is TOLD to use** (Levi 2026-09-08), which reverses the previous line here. `reply_to` is still set (see below) so a client who replies anyway reaches a human, and staff still record a relayed answer through `POST /cases/{id}/verification/response` — but the letter names `renewal@getstarted.hk`, and a screen or a page that tells an operator or a client to "reply to the email" is now wrong.
>
> **The client's confirmation page shows the approved Warning panel** (`public_approval._ask`): *"By clicking **Confirm & File**, you confirm that you have reviewed the draft and that the information is correct. The NAR1 will then be arranged for submission without further confirmation."*, and the button reads **Confirm & File**. The mock draws it as a **modal**; it is rendered **inline, visible on arrival**, because this route runs **no script at all** (`test_the_page_runs_no_script_at_all`) and a modal needs some. Inline says the same words at the same moment, before anything can be pressed. There is **consequently no Cancel** — in the mock it dismisses a dialog, and here there is no dialog to dismiss.
>
> **Confirm & File mails the client a RECEIPT** (Levi 2026-10-17; NAR1, ND2A, ND2B — `services/approval_receipt.py`, `email_service.approval_receipt_email`). Queued by `public_approval._record` as a background task **only after the claim** — never on a GET, a replayed press, a stale or expired link, or for the director who lost the race; not for a staff-relayed answer, the auto-approval or an ND2B waiver. To the token's address, `renewal@` copied and replying (the non-production lock applies inside `send`). It carries what the client confirmed: the frozen `verification_xml` rendered as the send renders it (named `…[-RevN].pdf`), plus an ND2A's written resolution — not the supporting uploads; a document that will not render is left off and named in the trail. The letter is the verification letter's family with a green "confirmation recorded" stamp (date, Hong Kong time), says **"confirmed"**, not "signed" (the CR signature is a separate act), and tells the reader to write to renewal@ at once if they did not confirm it. It never raises. One `EMAIL_SENT` row, `metadata.template = "approval_receipt"`, actor `G-FlowDesk (automatic)` — and **`GET …/verification/delivery` skips rows with a template**, or the receipt would be read back as the board's send. A Resend refusal is stderr only (no row would be true). `conftest._no_receipt_mail_in_tests` stubs the router's binding suite-wide.
>
> **The client's deadline is MANDATORY and the case worker picks it** (Levi 2026-09-07). `POST /cases/{id}/verification/send` requires `respond_by` (a calendar date, refused if it is in the past) and the Client Verification screen will not arm Send without one. It used to be `sent + 14 days`, computed inside the token issuer and chosen by nobody — and a fortnight is not a business rule: some clients are chased inside a week, and a return prepared months before its filing window should not have its link die long before anyone intends to file. **It is one value doing three jobs on purpose** — the date the letter prints, the moment the Confirm link stops working, and the moment `jobs.auto_approve_nar1` reads the client's silence as consent — passed as one argument (`nar1_approvals.issue(expires_at=...)`) so the message cannot promise a date the job does not honour. It expires at **23:59:59 Hong Kong** on the chosen day, not at midnight UTC, which would kill the link at 08:00 on the morning the client was given. `APPROVAL_WINDOW_DAYS` survives only for callers with no operator to ask.
>
> **A malformed address no longer refuses the whole send** (Levi 2026-09-07). It used to raise 422, so one typo'd chip left a three-director board unmailed. Since the send is one message per director there was never a reason the other two could not go: the bad address is reported by name **with its reason** in `failed` (alongside anything Resend rejects), the valid ones are sent, and the screen names **both** lists — who has it and who does not. A list with no valid address in it is still a 422, and names them. The check itself is unchanged: free text is never handed to Resend.

> **Every verification email after the first carries `[Rev. N]`, and an earlier revision's Confirm link is dead** (Levi 2026-10-02, migration 051). `nar1_cases.verification_revision` counts the emails that **actually went out**: the send computes `nar1_approvals.next_revision(case)` (stored + 1) to print it, and stores it only once at least one message has left, so a send Resend refused entirely does not use up a number. **Rev. 1 is unmarked** — it is the sample letter byte for byte; from Rev. 2 the subject reads `[Action Required] [Rev. 2] …`, the masthead and reference line carry it, the attachment is `…-Rev2.pdf`, and a notice above "Dear Client" says the earlier email's Confirm button no longer works. **Restart verification does NOT reset it**: the client still holds the earlier email.
>
> **SEND AGAIN RE-SENDS THE FROZEN COPY, UNDER THE SAME REV** (Levi 2026-10-03). A case already sent and not restarted mails `verification_xml` — the copy the client holds and the one the screen shows — as the **same** revision (`nar1_approvals.current_revision`), and builds nothing. **Only Restart verification moves to the next Rev**, because it clears that copy and the next send builds afresh. This reverses "every send is a new revision" and fixes a real mismatch: a draft case used to be **rebuilt from the live record** on every send while the screen kept showing the previous copy, so a client could be mailed a document the operator had never been shown. A case sent before the copy was kept (pre-046) is refused with `reason: "no_frozen_copy"` and told to restart. The screen says so beside the Sent line. ND2A/ND2B are unaffected: their screen offers no Send again before a restart.
>
> **A REVISED LETTER HAS ITS OWN WORDING** — the sample Levi sent on 2026-10-03 (`G-FlowDesk - revised NAR1 draft v.2.pdf`; not in the repo, its sentences are transcribed into `tests/test_email_service.py::REVISED_WORDING`), verbatim, deadline slotted in (`email_service._revised_wording`). Only the sentences change: layout, checklist, button, sign-off, footer and the no-link fallbacks are the first letter's. It says the revision follows "an update of the Director's particulars" on **every** revised letter, because that is the sample's wording. The notice box above "Dear Client" is labelled **"Revised draft"** with no number (the subject, masthead and reference line carry it).
>
> **Two locks on the old link.** `issue()` supersedes every outstanding token before minting the new revision's (unchanged), and each token now stores its `revision` — so `nar1_approvals.is_stale` refuses a link below the case's revision on the public page **and** in `jobs.auto_approve_nar1`, even when the supersede write failed. It is asked **before** the link's own outcome: a director who approved Rev. 1 used to be told "already confirmed" while Rev. 2 waited. Tokens issued before 051 keep `revision = NULL` (numbering them from history could come out one low and refuse a current link) until the case's **next** send, when `issue()` dates them `N-1` — exact at that moment, because every link already on the case belongs to an earlier send. **The auto-approval job also skips a link AHEAD of the case** (`is_ahead`): tokens are issued before the send loop, so a send that reached nobody leaves revision-N links on a case still at N-1, and silence about an email nobody received is not consent. The public page deliberately still honours such a link. **The backfill counts the audit trail first** and token batches only where there is no trail — a failed send leaves a batch behind. **ND2A and ND2B carry it identically**: `officer_changes.send_verification` numbers its sends the same way and `officer_changes/emails.py` prints them through `email_service.with_revision` / `revision_notice`, so the three forms cannot word it differently; the lock is in `public_approval._show`/`_record`, which serve both pages. **051 revises 049, not 050**: 050 is the ND2A/ND2B migration, revising 056 since the 2026-10-27 re-land (056 revises 051).

> **Three ND2 follow-ups (Levi 2026-10-18, migration 055).**
> - **A death asks for its date.** Deceased used to be pre-set only for people whose imported record already carried a date of death, and nothing let an operator enter one. On a natural person's Deceased cessation the drawer now requires **Date of death**, pre-filled from the profile, with the cessation date following it until the operator types their own. It is stored on `officer_change_entries.date_of_death`; `cases._death_date` refuses a future date, and a cessation date before the death. A resignation and a body corporate carry none. CR's ND2A has no box for it. **At Confirmation** (the write-back, `apply._apply_cessation`) it is written to `persons.date_of_death`, the profile's old value is kept in `entry.applied.person` for Undo, and both acts write a `PERSON_FIELD_UPDATED` row on the **person's** trail. The profile shows **Date of Death** only when there is one, so living clients get no empty row. An entry added before 055 has no date and writes nothing to the profile.
> - **Appointing a secretary lists Get Started HK Limited first.** The drawer asks **capacity first**, then who. With Company Secretary + Body corporate, GSHK is offered before anything is typed and leads the matches once something is. It is found by its BRN (`AppointmentDrawer.GSHK_BRN`, 67169839). A director appointment is not steered to it.
> - **The e-Sign route saves the signed form to the company's documents**, as the manual route's upload always did. After `submitForm`, `services/officer_changes/filed_form.save` renders CR's copy (`validated_xml`, full form, dated by `filed_on`) and stores it on the company as type `nd2a`/`nd2b`. The (id, version) pair goes in `nar1_cases.filed_form_document_id/_version`, and the save is audited as `OFFICER_SIGNED_FORM_UPLOADED` with `route: "esign"`. It never raises: a failure is a warning on the filing. Confirmation then offers **Save the signed form**, which uses the same `POST …/apply` retry; on the e-Sign route that retry now also runs when the profiles are done but the form is missing. That includes cases e-Sign filed before 055.

> **ND2A / ND2B after Jacqueline's feedback of 1 Oct 2026 and Levi's revisions of 4–5 Oct (migrations 052, 053; specs `docs/superpowers/specs/2026-10-02-nd2-jacqueline-feedback-design.md` and `…/2026-10-05-nd2-levi-revisions-design.md`, the second revising the first).** The chain is now `049 → 051 → 056 → 050 → 052 → 053 → 054 → 055 → 057`, one head (056: the 2026-10-26 duplicate-submission hotfix, which reached master and PROD first, so 050 was re-parented onto it on 2026-10-27; 054: CR status removed, see the Audit section; 055: the follow-ups below; 057: restates the case view with 056's stages, because 050/052/054 rebuild it from 047's text and would otherwise drop them).
>
> **An effective date may be blank when the client is sent the form, and is entered at Signing.** `rules` reports a missing date as a NOTICE; the send marks every undated change DEFERRED (`officer_change_entries.date_deferred`, `deferred` inside an ND2B item) and every dated one not — which is what makes a date filled in after an earlier send one the client has SEEN on the next. `PUT /officer-changes/{id}/entries/{entry_id}/effective-date` fills only a deferred date, never a future one, refuses once signed, and supersedes a CR-validated filing. **Nothing signs or files undated**: validate, sign, signed-form and record-filing answer 409 `dates_missing`. On e-Sign with a deferred date, Data Verification ends with `mark-checked {signing_method: "esign"}` and CR validates at Signing: `stageIndexFor`, `nar1_case_status` and 052's restated view all read that case as Signing. Changing the route clears `data_checked_at`, because the two routes check different things. A new ND2B line starts dated the open NAR1's return date, and **blank when there is no open NAR1** (Jacqueline, 2026-10-17: *"If there is no open NAR1, please keep it blank too. We can decide the effective date, as long as we can fill in the date before the submission."* — the six-week anniversary fallback is gone; `deadlines.anniversary_default`). The ND2B card says why a line is undated and that it is filled before filing.

> **Identification and addresses are per COMPANY** (Levi 2026-10-05, migration 053). A client may give one company a French passport and another a US one, or different addresses. `entity_officers.identity_document_id` / `residential_address_id` / `correspondence_address_id` say what ONE appointment files; **NULL follows the person** (default residential address, primary document of each type, correspondence "same as residential"), so a party nobody links files byte-for-byte as before. `services/appointment_links.py` is the one resolver, and it lives outside `services.officer_changes` because the NAR1 loader imports it: **the NAR1 (and therefore its drift check and an ND2A cessation) and the ND2B baseline/diff all read through it.** A linked document replaces the primary **of its type** and is moved to the front, because NAR1's mapper takes the FIRST document of a type, not the primary. `person_addresses` is the person's address book; `services/person_particulars.py` lists it as the UNION of the book and what is in use (so an address written by the older `PUT /residential-address` still appears), and every write there captures the ND2B baselines first and audits one `CASE_FIELD_UPDATED` row per company moved. The Person Profile shows **one Addresses card** — residential and correspondence, each address on ONE line in CR's order with its companies beneath, a line over CR's length named under it — and **each identity document's companies on the Identity Documents card** ("Filed for" + Companies…), not on a second card that listed the same passports again (Levi 2026-10-17: *"keep the design as simple as possible ... make sure the profile page is not bloated"*). One colour per company on every entry (by position in the person's list, never a hash: six companies, six colours); the page reads the book once (`useParticularsBook`). Correcting an address is copy-on-write for this person only. Shareholders' Schedule 1 addresses are not linked separately: a person who is also a member of the company files the address linked to their appointment there.

> **An ND2B filed for one company stops the same change being reported for the others** (Levi 2026-10-05; `particulars.dismiss_filed_elsewhere`, called from `apply`). Same CR item and same new value only, `source = 'dismissed'`, audited `OFFICER_PARTICULARS_DISMISSED` with `reason: filed_with_another_company`; a company with its own open ND2B is left to it.

> **One message per recipient, not one message with several recipients.** This also reverses a stated decision (*"a board of three directors is one message with three recipients ... one Resend failure cannot leave two directors informed and the third not"*). A shared link in a shared message would let any director approve in another director's name, which is a misattribution in a statutory record. The cost — partial failure — is handled by naming exactly which addresses failed (`failed_to`) rather than pretending the send was atomic. `renewal@getstarted.hk` is CC'd on **every** message and `reply_to` is on every one too — the case worker's first-message-only copy was removed on 2026-09-08, see above.
> **An administrator can reset a colleague's password, and it works exactly like creation** (`POST /users/{id}/reset-password`, `super_admin` only). The portal generates the password, mails it via `email_service.password_reset_email`, and sets `must_change_password` — so **the password is in the mail and in Supabase Auth's hash, and nowhere else**: not the response, not a log line, not an audit row. **The order is Auth, then flag, then mail, and nothing after the Auth call may raise.** By then the user's old password is already gone, and a 500 would report a failed reset to the administrator while the colleague was in fact locked out; the flag and the mail are therefore best-effort and *reported* (`must_change_password`, `reset_email_sent`, `reset_email_error`, `reset_email_redirected`), which the screen turns into "press it again once mail is working". It refuses a **deactivated** account (409 — banned in Auth, so the mail would be a live credential for an account that cannot sign in) and one with **no email** (409, before changing anything — no route out means no reset). **Not audited**, like every other user-management event; adding a code without seeding it would render unlabelled in the trail.
>
> **The confirmation names the account by EMAIL.** Two rows can carry the same display name, the mistake has no undo, and the address is the identifier that is actually unique.

> **`GET /auth/super-admins` is unauthenticated, and that is the point.** The login screen used to hardcode `levi@zenexflow.com` in both notices — the delivery contractor, not GSHK's administrators — so a locked-out GSHK user wrote to the wrong company and promoting somebody to `super_admin` changed nothing on screen. It returns the display name and email of **active super admins only** — never the rest of the user list, no ids, no `is_active` for anybody else, no `must_change_password` — takes **no parameter**, changes nothing, and is cached 5 minutes so reloading the login page is not a query generator. **A failure returns an empty list, never a 500**, and the screen then names nobody ("contact a Super Admin") rather than naming somebody wrong. Read it with `api.publicGet`, never `api.get` — the latter throws when there is no session, which is every visitor to that screen.
